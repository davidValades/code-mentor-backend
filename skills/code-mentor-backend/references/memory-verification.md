# Verify saving and continuity

Use when asked to test whether memory really saves, revises or resumes. Run during an active conversation, one step at a time. This is a storage check, not evidence of learning or educational efficacy.

1. Use memory-controls.md for read-only status. Confirm the actual authorized destination, source/version and current identity/revision. Without a destination, agree on one using the existing memory workflow; do not silently select a temporary folder or another project's root.
2. Establish scope before writing. Existing recording authorization covers normal learning notes; for a synthetic diagnostic use a separately authorized test root/document, labeled QA. Diagnostic success must never create learner evidence, achievements or a completed learning session. Explain that the test modifies that test document before acting; do not overwrite unrelated attachments or fixtures.
3. For a real session, use its actual covered material and observed responses. Save a note/checkpoint per study-notes.md and memory.md, verify content/identity/version and preserve a receipt. State what was actually saved and what remains pending. A record's activity date is not a verified save time.
4. Add a small actual continuation to that same session note. Before replacement, preserve native history or the prior immutable revision. Read back the same note ID, new revision, original creation date and history; update the index. On failure, retain the pending update and report which step failed. Never use a duplicate suffixed file to pretend replacement worked.
5. Ask for /status, /memory-audit and, for relevant material, /map. Check accessible links and exact evidence; do not count this diagnostic as new practice. Inspection commands themselves are read-only; map/notes writes use their separate authorized workflows.
6. To test a second conversation, provide a self-contained handoff with the actual destination/identity, note ID/revision, source date and next question. The user opens that conversation unless a real authorized tool supports it. The receiver reads the same destination and verifies identity/version before resuming. Without shared access, a limitation and continuity package is the successful fallback, not proof of cross-chat persistence. Reuse existing retry IDs for pending operations.
7. Report each step as verified, failed, or not tested, with actual tool evidence. Separate file mechanics, host activation, cross-conversation access, browser rendering and learner performance. Do not label the entire flow passed while one part is unobserved.

Read-only failure: leave the original unchanged, explain the blocker and preserve one pending package per session-close.md. No automatic Work activation, extra accounts, scheduled tests or browser-policy workarounds. In a car, defer document/screen interaction until stopped.

For a progress display check, the user opens the authorized private HTML in a permitted host. Check selected-day detail, filters/reset, keyboard/table fallback and narrow-screen layout against source evidence. A computational DOM test proves no actual rendering or CSP behavior. Do not bypass a blocked browser operation by serving the same file another way.
